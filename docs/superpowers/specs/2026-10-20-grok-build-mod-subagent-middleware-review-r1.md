## Spec Review (Round 1)

**Status:** Issues Found

**Issues (blocking planning):**

1. [§4.1/§7 crate layering] Cargo dependency cycle. `xai-grok-mods` needs `xai_grok_agent::{LoadedPlugin, AgentDefinition}` (catalog.rs, manifest.rs) and `xai_grok_tools::...::ChildControl`; §7 also adds `xai-grok-mods` as a dependency of `xai-grok-agent` (and §3.1 says `LoadedPlugin.dynamic_agents` is "populated by xai-grok-mods at plugin load"). xai-grok-agent -> xai-grok-mods -> xai-grok-agent is a cycle (xai-grok-agent/Cargo.toml already depends on xai-grok-tools). The same cycle exists for `run_mod_child`: it must call `ChildReporter<ShellChildRuntime>::started(StartedChild<ShellChildRuntime>)` and return `ChildRunOutput<ShellCompletionData>`, but `ShellChildRuntime` and `ShellCompletionData` (pub(crate), private fields, private `from_context`) live in xai-grok-shell, which depends on mods. The spec never gives the `run_mod_child` / `describe_mod_child` / `try_match_mod_provider` signatures (§3 calls them `ModRegistry::matches_subagent_type` / `ModProvider::type_summary`, §7 calls them `try_match_mod_provider` / `describe_mod_child`). Needed: decide crate direction (e.g. mods depends only on tools/types; generic `run_mod_child<C: From<ModChildControl>>` or a callback; agent crate only receives plain data) and fix the names.

2. [§3.1, §4.3, §7 dynamic catalog] Wrong against real types and unspecified load hook.
   - `AgentDefinition.model` is `ModelOverride` (`Inherit | Override(String)`), not `Option<String>`; `AgentDefinition` has a `pub(crate) builtin_name` field and no `Default`, so xai-grok-mods cannot build it by struct literal. Must use `AgentDefinition::parse`/`from_json` or a constructor added in xai-grok-agent.
   - Nothing says where/when `discover_mod_agents` runs. `PluginRegistry::from_discovered` (registry.rs:~175) is synchronous, is rebuilt per session and on `/plugins reload`, and would block up to 5 s per plugin spawning `node`. Needs: who calls it, sync vs async, caching/invalidations, and how this squares with the cycle in #1.
   - Qualified name rules are self-contradictory. Real lookup is `registry.get(plugin_name)` on `<plugin.name>:<agent>` (discovery.rs:~432-460) and `plugin_agents()` emits `format!("{}:{}", plugin.name, def.name)`. `mod.json.namespace` is not consulted, so `cursor:grok-4.7` resolves only if the plugin is named `cursor`, yet the reference plugin is `grok-cursor-subagents` (it would be `grok-cursor-subagents:grok-4.7`). The "or namespace when plugin.name == namespace" sentence is a no-op. Either require `plugin.name == namespace` or add a namespace alias in discovery (more diff lines).

3. [§4.2 containment] `runtime.command` is `"node"` in the example but the spec requires every `runtime.command` to be resolved under `canonical_root` and pass `starts_with`; bare `node` would always be rejected. Specify PATH-lookup rule for bare commands vs plugin-relative paths.

4. [§5.4 #2 admission lease] Ordering is wrong against `ActiveAgentMessageDelivery`. In the repo, `commit_admission` is the claim that must happen before the side effect ("`Admitted` is valid only when protected-row insertion succeeds inside `commit_admission`", coordinator_state.rs:~67). The spec sends `RunSteer`, waits for `SteerAck`, and only then calls `commit_admission`. By then the vendor has already consumed the steer; if the lease was revoked meanwhile (coordinator enforces the 5 s `ACTIVE_MESSAGE_ADMISSION_TIMEOUT` itself with `lease.revoke`, active_message.rs:~802), the host reports Rejected for a message the child acted on. Correct shape: `commit_admission(|| stdin_tx.try_send(RunSteer))` (closure is sync), then await `SteerAck`; define what happens on negative/missing ack after commit (cannot be rolled back) and drop the claim that the module enforces the 5 s itself. Also `ActiveAgentMessageOperation` has only `Queue | Steer`; `SteerOperation::Followup` has no source on this path.

5. [§5 wake/followup path] Not specified and partly wrong.
   - `deliver_initial_message` / `deliver_followup` are synchronous `-> bool` taking `&AgentMailboxMessage` (no lease, no ack). The spec says they delegate to `ModChildControl` and uses the `SteerAck` path; it must define the sync contract (e.g. `try_send` onto the writer channel returns true) and `accepts_native_message` (trait default is `false`, which silently rejects every native `send_message`/`followup_task` to a mod child; `NativeFollowup` is rewritten to `NativeMessage` before delivery).
   - Wake (`coordinator/wake.rs`) re-runs `ChildRunner::run` with the SAME `request.id`, a cloned original `request` (original `resume_from`, new `prompt` = message text) and `wake_origin: Some(..)`. The spec's "lookup `prev_id` from `resume_from`" is wrong for wake: the key is `request.id`, and `resume_from` may be stale. Wake also requires `reporter.started_deferred(...)` then `reporter.settle_deferred_start(bool)` (handle_request.rs:~1957+), which the spec never mentions (only `started`). `supports_wake()` must stay true and per-run-process semantics after `interrupt()`/completion should be stated.

6. [§3.3/§5/§1.3 child lifecycle & presentation] `run_mod_child` must reproduce what `run_shell_child` does around the coordinator, and the spec omits it: (a) resolve definition + `gate_subagent_type` at spawn time (handle_request.rs:402-406; `validate_type` is only called by the Task tool, not by Rhai `ChannelBackend.spawn` or v2 spawns, so §3.1's "automatically enforce toggles/allow-list" is false for those paths when the mod branch bypasses `run_shell_child`); (b) publish `SubagentSpawned`, `write_subagent_meta`, and set `ShellCompletionData::mark_spawned_notification_emitted` — `present_child_completion` only emits `SubagentFinished` if that flag is set or the run is background; (c) fill `StartedChild` (`child_session_id`, `child_cwd`, `effective_model_id`, `definition_background`, `persona`, `resumed_from`) and `ChildRunOutput.snapshot_ref`; (d) mapping `RunCompleted` -> `SubagentResult` (`cancelled`, `turns`, `tool_calls`, `tokens_used`/`output_tokens_used`/`total_tokens_used`, `duration_ms`, `child_session_id == subagent_id`, `warnings`). Also no code-level path exists for xai-grok-mods to emit ACP `SessionUpdate` (shell-private type) for `TextDelta`/`VendorToolActivity`; define a sink trait. `SubagentTracker`, cited as the native renderer in §1.3, does not exist in the repo; `SessionUpdate::SubagentProgress` does, and nothing says who emits it for mod children.

7. [§5.4 #4 / §3.4 structured output] Does not match the Rhai host. `HostService::spawn_agent` sets `runtime_overrides.output_schema: None`, wraps the prompt with `contract_prompt`, and validates `result.output` text via `validate_contract_output` (fenced ```json block, else brace-span). So `RunStart.output_schema` never receives a value from workflows, `SubagentResult` has no `structured_output` field ("keeping raw structured_output intact" has no channel), and appending a `<subagent-handback>` footer to `output` can corrupt candidate extraction. Define: `output` = `final_text` (with JSON fenced when `structured_output` present), footer only when no schema contract is detectable, and whether the schema is conveyed by prompt only (as native children do). Also note the retry passes `resume_from = result.child_session_id` of the previous attempt with a NEW child id.

8. [§6 tool bridge execution path] Undefined. (a) `bridge.rs` is said to use `ctx.parent_mcp_pool` (`SharedMcpPool`, shell-internal) and `ctx.parent_tool_definitions` (`Vec<ToolSpec>`, schemas only, no executors); xai-grok-mods cannot name these types and nothing executes workspace tools like `read_file/grep/glob/list_dir` (names unverified against the repo's actual tool ids). Need an injected `ToolExecutor` trait (or equivalent) and a stated execution/permission path (PreToolUse hooks via `ctx.client_hooks`, sandbox, plan-mode). (b) No `tool.call` request/response frame types or error codes exist in §5, `BridgedToolSchema` is undefined, and `tool.call` is described as "NDJSON" only in §1. (c) §5.1 says the Unix socket carries "tool bridge and steering", §5.4 sends steering over stdin; pick one. (d) Vendor-native shell/file tools run inside the sidecar outside Grok-Build permission/sandbox; the spec only passes `read_only: bool`. State the trust/enforcement boundary explicitly. (e) How `read_only` is derived is ambiguous: catalog `readOnly`, `provider.read_only`, `capability_mode == ReadOnly`, and "parent in Plan mode" (no source for the last in `ShellChildRunner::run`).

9. [§7 upstream budget] Hard cap of 60 lines and "4 files" are not credible/consistent: §2 says ~48, §7 says ~56. Missing touch points: construction sites for `LoadedPlugin` struct literals (registry.rs:175, discovery.rs:675, skills.rs:1496 and :2322, shell extensions/plugins.rs:191), the `ShellChildRuntime {..}` constructor at handle_request.rs:1956 and child_runtime_tests.rs:86 (5th/6th files), three Cargo.toml edits plus Cargo.lock, the catalog-load call site, and ~40+ lines for seven delegating methods with full signatures. Re-baseline and define whether tests and Cargo.lock count against the cap.

**Recommendations (advisory):**
- §1.2 says "persistent NDJSON sidecar daemon" but §5.1 is one process per run; align wording.
- Unix socket path `<plugin.data_dir()>/run-<uuid>.sock` (~/.grok/plugin-data/<plugin_id>/...) can exceed the 104-byte `sun_path` limit on macOS; use a short runtime dir (e.g. `$TMPDIR/grok-mod-<8hex>/`).
- `defaults.maxConcurrentRuns: 8` duplicates `SubagentLimits`; drop it (YAGNI). `readOnlyInPlanMode` is likewise unreferenced.
- `sessions.json` read-modify-write needs a lock across concurrent children in-process.
- Line citations drift: `plugin_agents` is discovery.rs:329 (not :335), `all_subagents_with_plugins` :360, `by_name_in_cwd_with_plugins_and_home` :432 (not :451), `ACTIVE_MESSAGE_ADMISSION_TIMEOUT` is coordinator_state.rs:46. `intel/*`, `DELUXE-SPEC.md`, `dunce`, `write_secure_file` (xai-grok-shell-base secure_file.rs) all exist.
- Verified OK: branch/commit 2fcd9729, `ChildControl` trait (7 methods) and `ChildRunRequest` (coordinator_state.rs:125), `commit_admission`, `WorkflowHostRequest::SpawnAgent` (host.rs:74), `validate_subagent_type` :2050 / `gate_subagent_type` :2081, `SubagentDescribeOutcome::Ok(SubagentTypeSummary{can_read,can_search,can_execute})`, `native_agents.json`, `SubagentCapabilityMode::ReadOnly`.
